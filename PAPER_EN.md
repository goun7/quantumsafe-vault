## Abstract

QuantumSafe-Vault is a self-custodial Bitcoin vault that (i) renders taproot key-path spending **mathematically impossible**, (ii) requires **two independent signatures** for every normal spend — one classical Schnorr, one gated by a post-quantum (PQC) hardware enclave — and (iii) *intends* to pin every unvault transaction to a **single staged output** with a 144-block CSV cooldown — implemented today as a transaction builder, not as a consensus covenant (§4 carries the correction). Inheritance is a Dead Man's Switch: a self-churn heartbeat keeps the vault provably alive; silence for ~180 days (26,280 blocks) unlocks a 2-of-3 heir settlement whose identities are hash-bound to ML-DSA-65 (FIPS 204) attestations.

The reference implementation (this repository, Rust) passes **169 tests**, including consensus-level verification against `libbitcoinconsensus` for **all four MAST leaves** (T7: every leaf spends from a real signed reference witness, tamper-rejected; T8: the Miniscript policy layer and the on-chain tree are proven consistent) and **live end-to-end tests on a real bitcoind v28.2 node**: the vault lifecycle, a BIP-174/371 PSBT device-signing round trip whose assembled transaction the node accepts into its mempool, the estate-letter flow (issue with QR → verify 8/8 → fund the letter's address → single flipped byte exits 1) and the **Phase-2 live-PSBT flow** — `psbt-live` discovers the vault's REAL confirmed UTXO via `scantxoutset` (no wallet ownership), builds the BIP-174/371 PSBT from the live outpoint, both devices sign, the coordinator finalizes and broadcasts, and the mempool ACCEPTS; a second run proves the largest-coin selection and the fail-closed refusal when nothing funds the vault; a third run consolidates MULTIPLE live coins into ONE multi-input spend (`--min-inputs`, largest-first selection, full BIP-371 taproot context including `tap_merkle_root` on every input so Coldcard/Ledger re-derive Q per BIP-341). The owner's **heartbeat rotation** (`vault-rotate`) performs the self-churn refresh against a live node — the coin re-deposits at the SAME address with the CSV clock reset — and re-attests every heir's ML-DSA-65 identity before the coin moves (a stale or forged heir identity aborts fail-closed). The **watchtower→co-signer alarm mirror** turns the read-only alert into enforcement: a vault whose heartbeat is due is frozen at the enclave, which refuses ALL signing requests for it — even with a perfectly valid ML-DSA-65 proof (fail-closed, per-vault; Theorem 1 degrades safely). The lock is a REAL service: `cosigner-bridge` serves the enclave over TCP with the alarm state re-read from the watchtower state file PER REQUEST (a daemon refresh takes effect without a restart), `vault-rotate --cosigner` obtains the second signature through the PQC gate and verifies it under the pinned enclave key, and `vault-rotate --inventory/--vault-id/--state-dir` reuses the watchtower's inventory schema with a due-gate and a persisted baseline (an early re-rotation is refused; rotation state and watchtower alarms can never contradict). The Round-14 operations layer closes the loop: `vault-rotate --inventory --all` sweeps EVERY due vault in one operator action (ONE coin, ONE refresh per sweep — ids sharing the estate address are recorded under the same tip/txid without re-broadcasting), the co-signer exposes per-vault Prometheus counters (`qsv_cosigner_refused_by_vault_total{vault=…}`, deterministic row order), the dev bridge speaks optional TLS (`--tls-cert/--tls-key`; mandatory for any non-loopback bind — plaintext co-signatures off loopback are refused at boot) with a thread-per-connection accept loop, and the mempool policy claims (RBF opt-in via `Sequence::ENABLE_RBF_NO_LOCKTIME`, no-dust outputs, exact operator feerate) are pinned by live `testmempoolaccept` tests against bitcoind v28.2 — including the BIP-125 asymmetry (a signalling original is replaceable by a higher fee, refused by a lower one). The Round-15 hardening closes the remaining operational gaps: the multi-vault sweep runs behind a LIVE co-signer gate (`--cosigner-all` — a watchtower-frozen vault is skipped with an explicit report and never recorded as refreshed, while an unanswerable gate fails the sweep closed before any ceremony), the dev bridge upgrades to MUTUAL TLS (`--tls-client-ca`: the handshake itself demands a client certificate chaining to the operator's CA, so an anonymous client never completes a session; the pinned identity releases the same deterministic signature), the `/metrics` exposition gains a fixed-bucket Prometheus latency HISTOGRAM (cumulative `_bucket{le=…}` rows beside the unchanged legacy counter), and watchtower webhooks become at-least-once (fixed-backoff retry within the pass, per-vault `webhook_delivery` recorded in the state file — the exit code stays the primary alarm channel). Round 16 hardens the operator surface further: the sweep can speak MUTUAL TLS to the gate bridge (`--cosigner-all-cert/--cosigner-all-key/--cosigner-all-ca` — a wrong-CA identity fails the gate closed before any ceremony; the pinned identity carries gate probes AND rotation signatures through one encrypted channel via a unified `BridgeClient`), a `--dry-run` preview classifies every inventory row and names the actions without writing state or broadcasting, the bridge gains a per-vault token-bucket rate limiter (`--rate-limit <capacity>:<refill>` — a flood from one vault cannot consume a sibling's budget; refusals counted in `qsv_cosigner_rate_limited_by_vault_total`), and webhook alerts can carry an `X-QSV-Signature: sha256=…` HMAC-SHA256 tag over the exact body (`webhook_secret`; RFC 4231-verified, relay-side content authentication). The FROST threshold wizard (docs/04 §4) is implemented: trusted-dealer key generation, SLIP-0039-sealed share backups (printed words), and the RFC 9591 ceremony whose aggregated 2-of-3 signature verifies as PLAIN BIP-340 Schnorr under the GROUP key — proven end-to-end through the real CLI binary. The **inheritance watchtower** (`watchtower`) performs one read-only pass — heartbeat DUE ⇒ ALERT (exit 1), inheritance CSV countdown, live coins — and with `--deal` runs a REAL RFC 9591 ceremony in `--no-broadcast` mode, proving threshold readiness TODAY with a deterministic hold artifact and a structurally impossible false-alarm path. The MAST tree carries **four leaves**: normal hybrid, clawback, inheritance, and the post-Q-Day emergency kit — a 37-byte commit-reveal leaf (`OP_DUP OP_SHA256 <H(pk_em)> OP_EQUALVERIFY OP_CHECKSIG`) whose plaintext destination key exists only inside a WOTS+-sealed offline kit. Empirical finding pinned by a regression test on the Bitcoin Core v26.2 engine: witness stack elements above 520 bytes are consensus-illegal (BIP-342 initial-stack discipline), so the 2,144-byte WOTS+ signature itself can never satisfy a tapscript check — the seal is verified air-gapped before broadcast, and the chain sees classical Schnorr only (T6).

## 1. The Quantum Threat Model, 2026 State of the Art

- **Shor's algorithm** breaks ECDSA and Schnorr in polynomial time once large fault-tolerant machines exist; Grover weakens (but does not break) SHA-256.
- **Gidney (2025, arXiv:2505.15917)**: fewer than 1 million noisy qubits suffice to factor RSA-2048 in under a week — a ~100× algorithmic improvement over prior estimates.
- **Babbush et al. (2026, arXiv:2603.28846)**: 256-bit ECDLP in roughly **1.2–1.45K logical qubits** (< 500K physical qubits under realistic error budgets).
- **Hardware 2026**: QuEra leads with 96 logical qubits; Microsoft + Quantinuum demonstrated 12 logical qubits at 2·10⁻³ error rates; IBM plans Starling (~200 logical qubits) for 2029.
- **Exposure**: Project Eleven (May 2026) estimates **~6.9M BTC** sits in P2PK and reused-segwit outputs vulnerable to a classical-public-key attacker; Coinbase's advisory board estimates ~7M. A consensus **Q-Day window of 2030–2042** (base case 2033) is the planning horizon of this design.

**Adversary classes**: (A) harvest-now-decrypt-later key attackers, (B) mempool sniffers (classical, active today), (C) key-loss and inheritance failure — statistically the largest realized loss class in 2026.

## 2. Architecture: A Two-Layer Hybrid Vault

The vault output is a P2TR with three MAST leaves behind a **NUMS (Nothing-Up-My-Sleeve) internal key**:

```miniscript
or_d(
    and_v(v:pk(key_user), pk(key_enclave)),                    /* normal hybrid */
    or_c(
        and_v(v:older(144), pk(key_recovery)),                 /* 144-block clawback */
        and_v(v:older(26280),                                  /* ~180-day inheritance */
            thresh(2, pk(key_heir_1), pk(key_heir_2), pk(key_executor)))
    )
)
```

1. **NUMS internal key** — derived as `SHA-256(seed-text || LE32(counter))` with the canonical smallest counter frozen by test. No discrete log exists by construction (SHA-256 preimage resistance), so the taproot key path is **provably unspendable**: a quantum attacker who steals the user's classical key still cannot walk the key path (Theorem 2).
2. **Leaf 1 — normal hybrid spend** — `<pk_user> CHECKSIGVERIFY <pk_enclave> CHECKSIG`. Exactly two signatures, in witness order `[σ_enclave, σ_user, script, control]`. The enclave key is a real BIP-340 keypair whose release is gated by a FIPS 204 ML-DSA-65 verification (Theorem 1).
3. **Leaf 2 — recovery clawback** — after 144 blocks, a recovery key can sweep the staging output if the owner detects a fraudulent unvault.
4. **Leaf 3 — inheritance** — after 26,280 blocks (~180 days) of vault silence, a 2-of-3 threshold of heirs (user, executor, beneficiary keys) settles without any online service.

## 3. The PQC-Gated Enclave Co-Signer (Theorem 1)

The second signature never comes from an offline human key. Instead:

- `qsv-pqc` derives a real Schnorr enclave keypair from a seed and **fail-closed** verifies an ML-DSA-65 (FIPS 204) signature over the sighash before releasing the Schnorr signature. Key sizes 1,952 B; signatures 3,309 B.
- In production the signer runs inside an **AWS Nitro Enclave** (or equivalent TEE). This repository ships `qsv-cosigner`: a deterministic, allowlist-enforcing TCP co-signer service (protocol v1) with signed provisioning documents. The dev-mode attestation document is simulated; the protocol contract (fail-closed, deterministic, allowlist) is preserved verbatim in a production TEE.
- A quantum attacker who factors/derives the user's classical key still lacks the enclave's PQC gate: **theft requires breaking both crypto systems and the TEE**.

## 4. Unvault Covenant & Theft Response (Theorem 3)

**Errata (Round 41, measured).** The covenant described here is not
implemented on-chain. Taproot scripts cannot constrain a transaction's
outputs, and the four leaves contain no such constraint: a spend of leaf 1
(user + enclave) that pays an arbitrary attacker address is ACCEPTED by
`libbitcoinconsensus`. Output pinning lives only in `unvault::build_unvault_tx`.
The recovery leaf (`<144> CSV DROP <pk> CHECKSIG`) applies to the vault output,
so the single recovery key becomes usable 144 blocks after each refresh and
stays usable; it cannot reach the staged output, which is a plain single-key
script. There is therefore no in-flight clawback and no veto window. A real
covenant requires `OP_CTV` (BIP-119) or an equivalent consensus rule, which is
the Phase-2 item now recorded in Module 11. What remains true is the
verification discipline: every constructed spend is checked by the reference
interpreter, and the tampered-signature case is rejected (Theorem 5).

## 5. Heartbeat & Sovereign Inheritance

- `qsv-core::heartbeat` implements the Dead Man's Switch: a policy (default 12,960-block period, 1,008-block margin) computes `is_due`, `blocks_until_expiry`, and builds a **self-churn refresh transaction** back into the same vault — the only regular on-chain act a healthy owner performs.
- If no refresh lands before expiry, leaf 3 activates. Heir identity sealing: each heir's classical key is hash-committed into an ML-DSA-65 identity attestation, fail-closed at verification time — impersonation requires breaking FIPS 204.
- Minimal human-in-the-loop: one signature per period in the happy path; everything else (gate checks, covenant construction, CSV enforcement, threshold verification) is deterministic code.

## 6. Hardware Signing: BIP-174/371 PSBT Flow

`qsv-core::psbt` builds unsigned taproot PSBTs with `tap_scripts` / `tap_internal_key` fields, computes per-input sighashes for the taproot leaf, verifies device signatures, and assembles/finalizes the witness — the standard pipeline for Coldcard/Ledger co-signing without ever exposing the vault policy to blind faith in a GUI.

## 8. Competitive Landscape (2026)

Casa, Unchained, BitGo and Fireblocks sell collaborative multisig built on classical ECDSA — robust against key theft, **silent against Shor**. BIP-360 (P2MR, merged into the BIP repository February 2026) and BIP-361 (PQC migration and legacy-signature sunset) define Bitcoin's own migration path, but wallet-grade tooling does not exist yet. Project Eleven runs BTQ testnet PQC experiments; no production custody product combines PQC gating, covenants, and inheritance. That intersection is this project's moat.
